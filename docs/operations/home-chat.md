# ホーム・チャット — 日次処理と復旧

対象は `2026-10-27-home-chat`。承認済みの[設計](../sdd/specs/2026-10-27-home-chat-design.md)が正本。
[検証記録](../testing/home-chat.md)と、以前の[基盤運用](app-foundation-friends-ui.md)は別に保持する。
**本番へのデプロイ・ジョブ登録は未実施**。以下は承認された環境の担当者が実行する手順であり、登録済みという意味ではない。

## 時計と処理順

- 日次境界は **04:00 JST = 前日の19:00 UTC**。例: 10月29日04:00 JST は10月28日19:00 UTC。
- 当日の抽選確定は04:00以上、**04:05 JST / 19:05 UTC 到達前**。期限ちょうどは失敗側。
- 達成はサーバー受付が当日04:00以上、翌日04:00未満の分だけ。端末時刻や送信予約時刻では判定しない。
- 前日の締め → 関係予約適用 → 当日の抽選。`daily_cycle_runs` の
  `settlement_completed_at` / `relationships_applied_at` / `draw_finalized_at` が各チェックポイント。
  抽選失敗で締め・予約適用を戻さない。
- 候補は境界時点の友達履歴と境界までの予約履歴から決まる。遅れて現在の友達一覧で抽選し直さない。
  境界後に成立した友達とは即会話できるが、当日の達成対象へ追加しない。

## サービス認証と起動契約

実体: `supabase/functions/daily-settlement/{index,handler}.ts`、migration `0016_daily_cycle_runtime.sql`。

- `POST /functions/v1/daily-settlement`、クエリなし、本文は空または `{}` のみ。
- `Authorization: Bearer <SUPABASE_SERVICE_ROLE_KEY>` が必要。未設定・匿名・ユーザーJWTは401。
  Gatewayの認証だけに頼らず、ハンドラーでもサービス資格を照合する。
- 資格はサーバー側のsecret storeに保管。アプリの `EXPO_PUBLIC_*`、Git、ジョブログ、コマンド履歴へ書かない。
  正確な値・HTTPヘッダー・メッセージ本文・画像URLを監視ログに残さない。漏洩時は資格を失効・更新し呼出側も更新する。
- 公開RPC `advance_chat_day()` はサービス専用で引数なし。公開HTTP/RPCに日時指定を足さない。
  非公開 `advance_chat_day_at` はDB所有者のトランザクションテスト専用で、運用から呼ばない。

## スケジュール案と監視（未登録）

1. 承認されたジョブ基盤で毎日 **19:00 UTC** に上記POSTを起動する。
2. 加えて **毎分** 同じPOSTで再確認する。抽選期限前の再試行、19:05到達時の失敗確定、
   締め・予約処理の復旧、停止中に残った過去日を回収する。04:00の単発だけに依存しない。
3. タイムアウト・ネットワーク失敗・503は次の1分確認へ回す。締め・予約の障害復旧も継続する。
   抽選成功・失敗の確定を解除して再試行してはならない。
4. 重複起動は同じ入口を使う。DBのlifecycle advisory transaction lockと段階記録で直列化・再開する。
   ロック待ちを障害と誤認して手動で台帳行やロックを削除しない。

応答は `daily_key`, `processed_days`, `failed_days`, `retry_required`。
`retry_required=true` または `failed_days>0` は **503**、通常完了は200。RPC例外も503。
200だけで抽選完了を推測しない。現在日付とDB上の `draw_state` / `draw_finalized_at` を合わせて確認する。
成功済みの再確認で `processed_days=0` は正常。現在日の失敗は繰返し応答でも監視へ通知される。

監視対象（登録も別途承認が必要）:

- 毎分呼出の欠落、401/400/405（資格・呼出契約の誤り）、通信失敗/503、所要時間とロック待ち。
- 19:00後の未作成/未処理日、期限前の `pending` / `running`、19:05時点の未確定。
- `draw_attempts`, `last_error_code` (`draw_error`, `deadline`, `settlement_error`, `relationships_error`)、
  未完了チェックポイント、`failed_days`、古い未適用 `daily_user_results`。
- アラートは担当者に日付・エラーコード・遅延・件数のみを送る。個人会話やサービス秘密を含めない。

## 障害復旧手順

1. 対象環境、サーバーUTC時計、最後の成功時刻を確認。承認された読取権限で
   `daily_cycle_runs` の未完了日と各段階、`daily_user_results` の未適用分を調べる。
   通常ローカルDBのresetや本番/linkedへの試験変更は禁止。
2. 401なら資格・secret注入・呼出先を修正して同じPOSTを再実行。400/405なら本文・メソッド・クエリを修正する。
   DB接続・権限・ロック待ち・関数例外なら原因を解消し、同じ日時引数なし入口で再開する。
3. 古い日は台帳基準日以後の未完了日を古い順に処理する。保存済みの境界履歴から予約を適用する。
   収集前の不明な予約を推測しない。以前の未確定結果を飛ばして新しいStreakを適用しない。
4. 期限超過の未確定抽選は失敗・対象外へ確定する。後から成功へ変えず、割り当て追加もしない。
   成功済みは後の呼出失敗で失敗へ変えない。対象外日はStreakを維持する。
5. 保存済み結果の再適用でStreakを巻き戻さず、二重加算しない。達成済みの旧データを尊重し、
   導入前に不明だった日を未達として作らない。
6. 予約は境界までの履歴で適用し、友達解除とブロックを整合させる。キャンセル済み予約や境界後の変更を混ぜない。
   関係終了後も当事者の受付済み履歴は閲覧可能、新規送信は停止する。
7. 毎分確認の復帰、200/503の意味、現在日の最終状態、締め・予約チェックポイント、
   Streak/割り当ての二重生成がないことを確認し、日付・コマンド・実結果を記録する。
   仕様判断や台帳修復が必要なら人間へ戻し、SQLで仕様を上書きしない。

## 端末側の復旧との区別

- 通信復帰・前景復帰・Realtime再購読は正規queryを再取得する。イベントの内容を本文の正本にしない。
- 端末・アカウント・相手単位のFIFO。再試行は5秒から倍増、最大15分、既存のばらつき付き。
  自動送信は予約から24時間。期限超過は本人確認が必要で元の待機位置を維持する。
- 結果不明は未送信と断定しない。同じoperation/client keyで受付結果を確認し、別IDを作って二重送信しない。
- 関係終了を確認した待機は停止し、再び友達になっても自動復活させない。本人確認済みの新しい送信だけ受け付ける。
- 通常閲覧は表示した受信分のみ。明示的な「最新へ」だけが取得した最新位置まで解消する。
  取得後に到着した分へ既読上限を広げない。
- ログアウトは未送信件数・結果不明を説明し、確認後に処理停止、アカウントSQLite・永続画像・100MiB閲覧キャッシュを削除する。
  別アカウント資格で送信・画像取得・購読を再開しない。
- プッシュ配信、OS通知許可、通知起動、関係管理UI、編集・送信済み取消は今回の対象外。
