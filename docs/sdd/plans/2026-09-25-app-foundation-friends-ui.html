App Foundation and Friends UI Implementation Plan

Goal: 承認済み仕様に従い、登録から友達成立、プロフィール編集、オフライン再送と通知までをiOS・Androidの実データで完結させる。

Architecture: Expo Routerの画面を、アカウント別SQLiteキャッシュ・下書き・送信キューとSupabaseの認証済みサーバー処理へ接続する。操作ID、DBトランザクション、プロフィールの版番号で重複と競合を扱い、画像はアップロード完了後にプロフィールへ反映する。招待のWeb入口とOS連携、通知配信、実機検証までを順に接続する。

Tech Stack: Expo SDK 57、React Native 0.86.3、React 19.2.3、TypeScript、Expo Router、expo-sqlite、Supabase Auth/Postgres/Storage/Edge Functions、Expo Notifications、Jest/jest-expo、React Native Testing Library、pgTAP、Deno tests。

Spec: docs/sdd/specs/2026-09-25-app-foundation-friends-ui-design.md

Global Constraints

  • ホームとチャットは画面の枠・準備中表示まで。ホームには友達追加の入口を用意する。
  • 毎日の抽選・進捗・会話機能、友達削除・ブロック操作、追加OAuth連携、毎日の通知は後続の実装単位。既存ブロック関係による検索・申請制限は今回扱う。
  • スマートフォンの下部タブはホーム、チャット、友達、マイページの4つ。
  • 横幅900以上の論理サイズでは左の縦ナビゲーションと一覧・詳細の2列表示を使う。狭い場合や文字拡大で収まらない場合は下部4タブと1列へ戻す。選択中の相手・入力を保持する。
  • Apple・Googleのみでログインする。同じ検証済みメールによる既存の自動連携方針を維持し、異なるメールのアカウントを自動統合しない。
  • User IDは2〜20文字の半角英数字・アンダースコア。前後の空白を除去し、大文字・小文字を区別せず一意とするが表示の大文字・小文字は保持する。確定後は変更不可。
  • 2文字以上で入力停止から300ミリ秒後に検索する。入力変換中は検索せず、古い結果で最新の結果を上書きしない。
  • 完全一致、前方一致、その他の部分一致の順とし、同分類ではUser ID順。20件ずつ表示し、もっと見るで追加する。
  • サーバーが受け付けた申請の有効期間は7日間。送信者は取り消し、受信者は承認・拒否できる。受信一覧に承認・拒否を置き、プロフィールも開ける。
  • 拒否後は送信側へ今回は成立しませんでしたと即座に表示する。拒否の明示・理由を出さないが、終了タイミングが伝わることを許容する。
  • 終了した申請は送信側で終了後7日間表示し、その後一覧から外す。表示期間は再申請の待機期間ではない。
  • 招待は7日間有効で複数人に共有可能。有効なリンク・QRを再表示し、期限切れ時に新規発行する。手動再発行は確認して実行し、以前の招待を無効化する。
  • 有料の専用リンクサービスは採用しない。AndroidはGoogle Play Install Referrerを利用して招待情報を取得する。
  • iOSの1回の貼り付け操作は、追加操作なしの自動復元方針に対する承認済み例外。自動クリップボード読取りを前提にしない。
  • 表示名は1〜15文字。前後空白を除去し、空白だけ・改行は禁止。同名を許可し、登録後に変更できる。
  • 自己紹介は任意、200文字まで、改行可能。空に戻して削除できる。文字数は見た目上の文字単位で数え、改行は1文字とする。
  • 入力画像は10MBまでのJPEG・PNG・HEIC。最大1024×1024のJPEGへ変換し、透過部分は白背景、表示は円形とする。
  • 画像失敗時に文字だけ先に公開しない。本人には変更予定内容と送信状態、他人には以前の公開内容を表示する。
  • 接続復帰・アプリ復帰で再試行する。一時失敗は5秒から倍増、最大15分間隔で小さなばらつきを加える。自動再試行では期限を延長しない。
  • 送信待ち期限は24時間。超過した未送信操作を自動実行せず、内容と最新状態を確認して新しい操作として再送する。実行不能なら理由を説明する。
  • 送信済みで結果不明の操作は、24時間超過だけで未実行と断定しない。結果確認を区別する。
  • 申請到着、承認・相互申請による成立、申請の7日間の期限切れをプッシュ通知する。拒否と招待リンク自体の期限切れはプッシュしない。
  • 時間帯指定の初期値はライト07:00、ダーク19:00。両方を変更可能で、同じ時刻は保存不可。端末の現地時刻を使い、閉じている間に時刻を過ぎたら復帰時に反映する。

  • app/src/ui/、app/src/navigation/、app/src/theme/: 共通部品、画面分割、起動判定、テーマ。既存の業務モジュールはapp/src/auth/、profiles/、discovery/、invitations/、requests/で拡張する。
  • app/src/storage/、app/src/sync/、app/src/backend/、app/src/notify/: SQLite、送信処理、APIアダプター、通知。画面統合テストはapp/__tests__/に置く。
  • supabase/migrations/0007_command_boundary.sql〜0013_notification_delivery.sql: 新しい権限・操作記録、登録、申請、検索、招待、プロフィール、通知の追加マイグレーション。既存0001〜0006は書き換えない。
  • supabase/functions/_shared/、app-command/、app-query/、notification-dispatch/、device-session/: サーバー共通検証、更新・参照API、通知ワーカー、端末登録。既存friendship-admin/とrequest-expiry/は安全な共通処理に接続する。
  • supabase/tests/database/、supabase/functions/tests/、scripts/test-local-backend.mjs: pgTAP、関数テスト、実際のローカルAuth/Data APIを使う統合テスト。
  • invite-web/index.html、invite-web/app.js、invite-web/styles.css、invite-web/runtime-config.js、scripts/build-invite-web.mjs: フレームワークを追加しない招待Web入口と配信用ビルド。
  • docs/testing/app-foundation-friends-ui.md、docs/operations/app-foundation-friends-ui.md: 実機検証結果とOAuth・通知・リンク・定期処理の設定手順。

Execution and verification contract

  • タスクは番号順に実行する。各Taskは一つの引き渡し単位。テストを先に失敗させ、実装後に同じコマンドで成功を確認する。タスク内の手順は独立PRに分割しない。
  • app/AGENTS.mdに従い、コードを書く前に https://docs.expo.dev/versions/v57.0.0/ と利用するSDK 57のAPIページを読む。Context7はlibraryで解決後にdocsを取得する。現行版だけの例をSDK 57へ無検証で移植しない。
  • 計画作成時の基準は16スイート・90テスト成功、npm run typecheck成功。既存の正常系ヘルパーテストだけを完成証拠にしない。
  • 作業ディレクトリ指定がないコマンドはリポジトリルートで実行する。npm --prefix appはapp/のスクリプトを実行する。新規テスト名は各Taskが作成する実ファイル名である。
  • DB検証は専用のローカルSupabaseで実施する。初期化はnpx supabase start、続いてnpx supabase db reset --local --no-seed。resetはローカル検証データを消すため、作業用DBに未保存データがないことを確認する。remote/linkedのresetを使わない。
  • config.tomlは存在しないseed.sqlを参照している。新しいテストは独立fixtureを作り、固定日付の旧seedをそのまま実行しない。ローカルAuthの実ユーザーを生成し、テスト終了時に削除する。
  • 各Taskは対象のテストに加えてnpm --prefix app run typecheckを実行する。Edge FunctionsのHTTP統合検証では別プロセスでnpx supabase functions serveを起動する。全体回帰はTask 22で行い、新規失敗があれば関連Taskの完了を見直す。
  • 必要な外部入力は実際のiOS bundle ID、Android package、Apple team ID、App Store ID、Android署名SHA-256、HTTPS招待ドメイン、Supabase URL・公開キー、OAuth設定、通知資格情報、検証端末とストア配布権限。値を捏造しない。コードは環境変数で受け取り、不足ならビルド・配信前チェックを失敗させる。
  • 外部設定が未提供でも純粋処理・ローカル統合は進められるが、OAuth実通信・ドメイン関連付け・プッシュ・ストア検証を成功扱いにしない。必要な工程で利用可能な設定を確認し、阻害条件と残る検証を報告する。

  3. index.tsは必要な起動処理の後でexpo-router/entryを読み込む。ルートはsrc/appに統一する。4つの日本語ラベル、ホーム・チャットの準備中、友達・マイページの到達先を実装する。未実装の業務操作を成功表示しない。
  4. 検証: npm --prefix app test -- --runInBand __tests__/navigation-shell.test.tsx __tests__/scaffold.test.ts。4タブ表示と入口が一致すること。app/でnpx expo install --check、npx expo config --type publicも実行し、SDK整合性を確認する。

Task 2: 認証済み操作境界と実DBテスト

  1. supabase/migrations/0007_command_boundary.sql、functions/_shared/auth.ts、_shared/commands.ts、app-command/index.ts、functions/deno.json、tests/database/command-boundary.test.sql、functions/tests/command-boundary.test.ts、scripts/test-local-backend.mjsを作る。
  2. actorは検証済みJWTから求める。operation_id、kind、payload、payload_hash、actor_id、確定結果を保存し、同一actor・IDの同一内容は同じ結果、異内容は競合にする。操作記録と業務変更は同一DBトランザクション内で確定し、クライアントがactorを偽装できない構成にする。
  3. 0006の直接書込みによる承認迂回、既存create_friendship_from_requestの無制限実行、未検証friendship-admin経路を閉じる。読み取りは必要な範囲を維持し、更新は専用境界へ寄せる。SECURITY DEFINER関数は固定search_pathと限定EXECUTE権限を持たせる。
  4. ローカルテストrunnerはSupabase statusの機械可読出力から接続情報を内部取得し、秘密値をログしない。実Authユーザー2人と第三者を作り、未認証・偽装・直接テーブル/RPC呼出しを拒否する。検証: npx supabase test db、deno test --allow-env --allow-net --config supabase/functions/deno.json supabase/functions/tests/command-boundary.test.ts、node scripts/test-local-backend.mjs --suite command-boundary。

Task 3: 登録確定と共有入力ルール

  1. supabase/migrations/0008_registration_profile_version.sql、functions/_shared/profile-validation.ts、app/src/profiles/validation.ts、validation.test.ts、supabase/tests/database/registration.test.sqlを作り、既存registration.tsを接続する。プロフィール版番号と案内済み状態を追加する。
  2. registerとmark_onboarding_seenを操作境界に実装する。IDの正規化・変更禁止・原子的一意性、表示名の見た目上15文字、改行・空白、自己紹介200文字の共通fixtureをクライアント・サーバーで検証する。文字列.lengthやPostgres char_lengthを見た目上文字数の代用にしない。
  3. 不適合な既存データを切り捨てたり自動改名しない。事前検査で報告し、制約追加の移行を止める。新規登録・更新はサーバーでも同じルールを適用する。
  4. 検証: npm --prefix app test -- --runInBand src/profiles/validation.test.ts src/profiles/registration.test.ts、npx supabase test db、node scripts/test-local-backend.mjs --suite registration。大文字違い同時登録は一方だけ成功、絵文字・結合文字・境界値は両環境一致。

Task 4: 申請の原子的遷移と期限切れ

  1. supabase/migrations/0009_request_transitions.sql、functions/_shared/request-commands.ts、tests/database/requests.test.sql、functions/tests/requests.test.tsを作り、friendship-admin/index.tsとrequest-expiry/index.tsを修正する。
  2. request、approve、reject、cancelを操作境界へ実装する。新規は相手ID、決定操作はrequest_idを指定し、再申請後の別申請へ古い取消・承認を適用しない。未順序ペア単位のロックで逆方向同時申請、取消対承認、失効対承認を直列化する。
  3. サーバー時刻で7日を判定し、定期処理が遅れても期限切れ承認を拒否する。拒否は送信者向け結果で中立化し、申請中と終了履歴を分け、終了後7日だけ表示する。再申請は別IDで即時可能。成立と通知用のドメインイベントを一度だけ記録する。
  4. 検証: npx supabase test db、deno test --allow-env --allow-net --config supabase/functions/deno.json supabase/functions/tests/requests.test.ts、node scripts/test-local-backend.mjs --suite requests。runnerは並行HTTP要求で競合を再現し、古い申請ID・第三者・重複操作を検証する。

Task 5: 検索・プロフィール・一覧の参照API

  1. supabase/migrations/0010_discovery_queries.sql、functions/app-query/index.ts、functions/_shared/queries.ts、tests/database/discovery.test.sql、app/src/backend/queries.ts、app/src/discovery/lookup.tsとlookup.test.tsを作成・更新する。
  2. search_profiles(query,cursor)、get_profile(userId)、list_friends、list_requests(direction,cursor)の契約を実装する。IDのアンダースコアをLIKEワイルドカードにしない。完全一致・前方一致・部分一致と正規化ID・内部IDの安定キーで20件のページ境界を作る。
  3. 自分・双方向ブロック除外、友達・申請状態の付与、友達以外へのStreak非公開をサーバーで守る。公開DTOに拒否理由や私的進捗を出さず、未登録actorの検索を拒否する。旧resolveSingleCandidateは複数候補検索の入口として使用しない。
  4. 検証: npx supabase test db、node scripts/test-local-backend.mjs --suite discovery、npm --prefix app test -- --runInBand src/discovery/lookup.test.ts。21件以上、同名、大文字違い、_を含む検索、ページ重複、第三者のStreak参照を確認する。

Task 6: 招待発行・再発行・解決API

  1. supabase/migrations/0011_invitation_lifecycle.sql、functions/_shared/invitation-commands.ts、tests/database/invitations.test.sqlを作り、app-commandとapp-queryに招待処理を追加する。
  2. 招待の有効期限、明示的な失効、複数人利用を区別する。旧used_atを一回利用制限と解釈しない。get_or_create_invitationは有効な既存招待を返し、reissue_invitationは旧招待失効と新規発行を同一トランザクションにする。
  3. resolve_invitationは推測困難なトークンを検証し、確認用の相手情報だけを返す。申請確定時もトークンの有効性を確認し、画面表示後の再発行・失効をすり抜けさせない。招待の全件列挙を公開しない。
  4. 検証: npx supabase test db、node scripts/test-local-backend.mjs --suite invitations。複数人が同一招待から申請でき、再発行後の旧リンク・期限境界・同時再発行を確認する。

Task 7: プロフィール公開の版管理と画像所有権

  1. supabase/migrations/0012_profile_publication.sql、functions/_shared/profile-commands.ts、tests/database/profile-publication.test.sql、app/src/backend/profile.tsを作る。
  2. プロフィール更新はbase_version、変更項目、アップロード済み画像参照を受け取る。本人所有の画像の実在と形式を確認し、版番号一致時だけプロフィールと版番号を原子的に更新する。画像は専用バケット内のactor・操作ID別パスとし、他人のパスを参照できなくする。
  3. 競合時は最新公開内容と版を返し、無条件upsertを行わない。アップロード成功だけでは公開せず、他人からは公開プロフィールが指す画像だけ参照可能にする。文字だけ先に更新する分割処理を作らない。
  4. 検証: npx supabase test db、node scripts/test-local-backend.mjs --suite profile-publication。同版同時更新は一方のみ成立、未アップロード・他人画像で全項目不変、同一操作再送で版が二重増加しないこと。

Task 8: アカウント別SQLiteと永続下書き

  1. app/でnpx expo install expo-sqlite expo-secure-store expo-cryptoを実行する。app/src/storage/database.ts、migrations.ts、drafts.ts、cache.ts、files.ts、app/__tests__/storage.integration.test.tsを作る。
  2. SQLiteにはaccount_id付きキャッシュ、下書き、outbox、pending_invitation、device_settingsを定義する。キャッシュはfetched_at、outboxはoperation_id・kind・payload・base_version・created_at・expires_at・attempts・next_attempt_at・stateを持つ。書込みトランザクションと版付きスキーマ移行を実装する。
  3. 画像を永続領域へコピーしてから参照を確定する。途中失敗で壊れた参照を公開しない。SecureStoreは認証情報に使い、サイズ限界を超えるセッションは分割して復元できるアダプターを作る。アカウント破棄はキャッシュ・画像・下書き・キューを対象とし、テーマは残す。
  4. 検証: npm --prefix app test -- --runInBand __tests__/storage.integration.test.ts。SQL境界のテストに加え、開発ビルドで書込み→プロセス終了→再起動→復元を実行し、docs/testing/app-foundation-friends-ui.mdに実SQLiteの結果を記録する。モックだけを永続性の証拠にしない。

Task 9: 送信キューの状態機械とワーカー

  1. app/src/sync/types.ts、queue.ts、worker.ts、retry.ts、api.ts、queue.test.ts、worker.test.tsを作る。時計・乱数・ネットワーク・永続ストアを注入可能にする。
  2. enqueue、claim、cancelUnsent、reconcile、retryAsNewを実装する。claimと取消は同じSQLiteトランザクション条件で競合を解決し、前景・背景の二重claimを防ぐ。送信前に操作IDを永続化し、失われた応答は結果確認へ移す。
